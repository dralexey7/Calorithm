# PRD — Calorithm (MVP)

> Статус: **черновик, шаг 1 процесса** (`docs/development-workflow.md`). Требует ручной валидации автором.
> Документ описывает **потребности и поведение продукта**, а не реализацию. Технические/архитектурные решения принимаются на шаге 2 (`system-architect`).
> Дата: 2026-06-02 · Язык продукта и документа: русский.

---

## 1. Назначение

Calorithm — умный счётчик калорий с минимальным трением. Пользователь описывает съеденное **свободным текстом** (например «грамм 200 жареной курицы с гречкой», «тарелка куриного супа»), а система сама превращает это в структурированные позиции, определяет КБЖУ, сохраняет запись и помогает отслеживать дневное потребление.

**Ключевая ценность:** логирование еды без форм, поиска по базе и ручного ввода грамм — достаточно написать фразу.

**Архитектурный принцип продукта:** **ядро + подключаемые каналы коммуникации**. Вся логика (аккаунты, парсинг, КБЖУ, учёт, сводки) живёт в ядре; каналы — тонкие адаптеры. Первый канал — Telegram. Это требование к продукту (расширяемость каналов), а не указание реализации.

---

## 2. Цели MVP

| # | Цель |
|---|------|
| G1 | Пользователь логирует еду одним сообщением на естественном языке. |
| G2 | Система корректно выделяет позиции и количества (граммы и порции). |
| G3 | По каждой позиции определяется КБЖУ (OpenFoodFacts; при отсутствии совпадения — оценка LLM). |
| G4 | Записи хранятся per-user с изоляцией данных. |
| G5 | Пользователь видит, что съел за день, и итог по КБЖУ — по запросу и автоматически утром. |
| G6 | Соблюдение лимитов внешнего источника КБЖУ на уровне всей системы (без банов). |

## 3. Не-цели (Non-goals) MVP

- Цели/нормы потребления и прогресс к ним (сразу после MVP).
- Микро- и макроэлементы помимо КБЖУ.
- Полноценное редактирование позиций (в MVP только удаление по команде).
- Логирование задним числом и за произвольную дату.
- Смена часового пояса пользователем.
- Веб/мини-апп ВК и прочие каналы; фото- и голосовой ввод.
- Локальная копия БД OpenFoodFacts.
- Мультиюзер-SaaS, биллинг, веб-дашборд, мобильное приложение.

---

## 4. Целевой пользователь

Старт — 1–2 пользователя (вероятно сам разработчик). Архитектура и модель данных мультиюзерные с самого начала, но первоначальная нагрузка низкая. Платных/публичных сценариев в MVP нет.

---

## 5. Метрики успеха

| Метрика | Ориентир для MVP |
|---|---|
| Доля сообщений, успешно превращённых в записи (без ошибки) | ≥ 90% |
| Доля позиций с корректно распознанным составом и количеством (ручная оценка автором на выборке) | ≥ 80% |
| Точность классификации намерения «про еду / не про еду» (ручная оценка на выборке, US-017) | ≥ 90% |
| Доля позиций, по которым КБЖУ получено (OFF или LLM-fallback) | 100% (fallback гарантирует значение) |
| Авто-сводка приходит в 9:00 локального времени | 100% дней с записями |
| Инциденты бана/блокировки источника КБЖУ | 0 |

> Метрики качества распознавания на старте оцениваются вручную автором — автоматического ground truth нет.

## 6. Объём MVP

**Минимальный ценный цикл:**
свободный текст → распознавание позиций (состав + количество) → КБЖУ (OFF + LLM-fallback) → сохранение с изоляцией по пользователю → сводка по запросу + авто-сводка в 9:00 за прошедший день.

Вспомогательное в MVP: классификация намерения каждого сообщения (про еду / не про еду), регистрация пользователя при `/start`, per-user подтверждение распознанного, удаление записи командой, глобальное соблюдение лимитов источника.

**Осознанно вне MVP:** см. раздел 3 (Non-goals).

## 7. User stories

Формат: `Как [роль], я хочу [действие], чтобы [результат]`. Роль по умолчанию — «пользователь» (идентифицируется по Telegram user_id).

### US-001 — Регистрация при первом обращении · **Must**
Как новый пользователь, я хочу начать работу командой `/start`, чтобы система завела для меня аккаунт и я мог сразу логировать еду.

Acceptance:
- Given пользователь, которого ещё нет в ядре, When он отправляет `/start`, Then создаётся аккаунт, привязанный к его Telegram user_id, и приходит приветствие с краткой инструкцией.
- Given существующий пользователь, When он отправляет `/start`, Then повторный аккаунт не создаётся, данные сохраняются.
- Модель данных позволяет в будущем привязать к одному аккаунту несколько каналов; **механизм привязки в MVP не реализуется**.
- По умолчанию пользователю присваивается часовой пояс МСК.

### US-002 — Логирование еды свободным текстом · **Must**
Как пользователь, я хочу написать о съеденном обычной фразой, чтобы не заполнять формы.

Acceptance:
- Given сообщение, классифицированное как «про еду» (см. US-017), When система его обрабатывает, Then выделяются отдельные позиции (продукты) с составом и количеством.
- Given сообщение «грамм 200 жареной курицы с гречкой», When система его обрабатывает, Then выделяются отдельные позиции с составом и количеством.
- Given сообщение с несколькими блюдами/продуктами, When оно обработано, Then каждый продукт — отдельная позиция (одно сообщение может дать несколько продуктов).
- Given сообщение распознано как «про еду», When система формирует ответ, Then ответ содержит: **разбивку по продуктам**; по каждому продукту — **КБЖУ на 100 г** и **источник** (OFF/LLM); и **суммарные КБЖУ блюда** по фактически съеденным количествам всего ввода.
- Given сообщение принято, When оно обрабатывается, Then обработка **асинхронная**: ответ доставляется после обработки (допустима задержка) в **канал-источник**; промежуточная индикация «обрабатываю…» **опциональна** (например, нативный chat action канала) и не является обязательным требованием.
- Запись привязана к пользователю и к **текущему дню** в его часовом поясе.

> Ответ на сообщение (разбивка по продуктам + КБЖУ/100 г + источник + суммарный итог по съеденному) отличается от **дневной сводки** (US-007/US-008 — список позиций за день + итог за день).

### US-003 — Количество в граммах и порциях · **Must**
Как пользователь, я хочу указывать как граммы («грамм 200»), так и порции («тарелка», «штука»), чтобы писать как удобно.

Acceptance:
- Given явное количество в граммах, When позиция распознана, Then используется указанный вес.
- Given порционное описание («тарелка супа», «2 яйца»), When позиция распознана, Then система **оценивает вес в граммах** автоматически и фиксирует, что вес оценочный.
- Качество оценки веса зависит от промпта LLM (см. Risks).

### US-004 — Определение КБЖУ с fallback · **Must**
Как пользователь, я хочу, чтобы по каждой позиции считались калории, белки, жиры и углеводы, чтобы вести учёт.

Acceptance:
- Given позиция с количеством, When есть подходящий продукт в OpenFoodFacts, Then КБЖУ берётся из OFF и пересчитывается на количество.
- Given подходящего продукта в OFF нет (частый случай для готовых блюд), When КБЖУ нужно определить, Then его **оценивает LLM по своим знаниям**, и источник оценки помечается.
- Given одно сообщение распарсено на несколько продуктов, When определяется КБЖУ, Then **разные продукты одного сообщения могут иметь разные источники** (часть из OFF, часть — оценка LLM); у **каждого отдельного продукта источник один** (OFF либо LLM).
- Given любая позиция, When она сохранена, Then у неё всегда есть значения КБЖУ (fallback гарантирует результат).
- В MVP считаются только калории + Б/Ж/У.

### US-005 — Подтверждение распознанного (per-user настройка) · **Must**
Как пользователь, я хочу включать/выключать показ «вот что я понял» с подтверждением перед записью, чтобы при желании ловить ошибки распознавания.

Acceptance:
- Given у пользователя подтверждение **включено**, When сообщение распознано, Then бот показывает распознанные позиции (состав, количество, КБЖУ, источник) и ждёт подтверждения; запись создаётся только после подтверждения.
- Given у пользователя подтверждение **выключено**, When сообщение распознано, Then запись создаётся автоматически с кратким подтверждением.
- Настройка подтверждения — **per-user** (каждый пользователь управляет своим режимом). По умолчанию — **выключено** (автоматическая запись), см. A7.

### US-006 — Сохранение с изоляцией по пользователю · **Must**
Как пользователь, я хочу, чтобы мои записи были только моими, чтобы данные не смешивались с чужими.

Acceptance:
- Given записи нескольких пользователей, When пользователь запрашивает данные, Then он видит только свои.
- Каждая запись хранит: дату/время в часовом поясе пользователя, позиции (продукты), количество (с пометкой «оценочный вес»), КБЖУ, источник КБЖУ (OFF/LLM) **на уровне каждого продукта** (в одной записи продукты могут иметь разные источники).

### US-007 — Сводка по запросу · **Must**
Как пользователь, я хочу запросить сводку за день в любой момент, чтобы видеть, что и сколько съел.

Acceptance:
- Given у пользователя есть записи за сегодня, When он запрашивает сводку (команда), Then он получает список позиций за день и итог по КБЖУ.
- Обработка сводки **асинхронная**: запрос ставится в очередь, результат доставляется в **канал-источник** запроса (допустима задержка).
- Given записей за день нет, When запрошена сводка, Then приходит понятное сообщение, что записей нет.
- «День» считается в часовом поясе пользователя.

### US-008 — Авто-сводка в 9:00 · **Must**
Как пользователь, я хочу получать сводку за прошедший день автоматически утром, чтобы не запрашивать вручную.

Acceptance:
- Given наступило 9:00 локального времени пользователя, When у него были записи за прошедший день, Then приходит авто-сводка (позиции + итог КБЖУ за прошедший день).
- Given за прошедший день записей не было, When наступает 9:00, Then **сводка не отправляется** (принятое решение, см. A6).
- Сводка считается за **прошедший** календарный день в часовом поясе пользователя.
- Given у пользователя несколько активных каналов, When отправляется авто-сводка, Then она доставляется **только в основной (primary) канал** (пользователь может сменить primary).

### US-009 — Удаление записи командой · **Must**
Как пользователь, я хочу удалять ошибочную запись специальной командой, чтобы сводка оставалась корректной.

Acceptance:
- Given пользователь-разработчик (per-user признак, см. A10), When он смотрит свои записи, Then у каждой записи виден **идентификатор**.
- Given у пользователя-разработчика есть записи, When он вызывает команду удаления по видимому идентификатору записи, Then запись удаляется и перестаёт учитываться в сводке.
- Удаление **только командой**, не свободным текстом.
- Удалить можно только свою запись.
- Для обычных (не-dev) пользователей упрощённый UX удаления (например выбор из списка без ручного ввода идентификатора) — после MVP (см. A10).

### US-010 — Соблюдение лимитов источника КБЖУ · **Must**
Как владелец системы, я хочу, чтобы обращения к OpenFoodFacts укладывались в его лимиты, чтобы не получить бан.

Acceptance:
- Given несколько пользователей делают запросы, When система обращается к OFF, Then соблюдается **общая на всю систему** стратегия лимитов.
- Given лимит близок/исчерпан, When нужно КБЖУ, Then система деградирует штатно (например, через LLM-fallback) без падения и без бана.
- Стратегия лимитов — глобальная (продуктовое требование; механика — шаг 2).

### US-017 — Распознавание намерения сообщения · **Must**
Как пользователь, я хочу, чтобы система понимала, пишу ли я о еде или это обычное сообщение, чтобы случайный текст не превращался в запись.

Acceptance:
- Given любое входящее **текстовое** сообщение, When система его получает, Then она классифицирует его как «**про еду**» или «**не про еду**».
- Given сообщение классифицировано как «не про еду», When это определено, Then пользователь получает понятный ответ (что сообщение не распознано как описание еды) и **запись не создаётся**.
- Given сообщение классифицировано как «про еду», When это определено, Then система переходит к разбору и обработке как в US-002.
- Given сообщение «про еду», но из него не извлекается ни одного осмысленного продукта, When это определено, Then оно трактуется как «не про еду» / просьба переформулировать; запись не создаётся (см. A11).

### US-011 — Цели и нормы КБЖУ · **Should (следующая версия)**
Как пользователь, я хочу задать дневную норму КБЖУ и видеть прогресс, чтобы управлять питанием. *Вне MVP, ближайший приоритет после MVP.*

### US-012 — Редактирование позиций · **Could**
Как пользователь, я хочу корректировать распознанные позиции (вес, состав), чтобы исправлять ошибки без удаления. *Вне MVP.*

### US-013 — Смена часового пояса · **Could**
Как пользователь, я хочу менять часовой пояс, чтобы сводки приходили вовремя при переезде. *Вне MVP.*

### US-014 — Логирование задним числом · **Could**
Как пользователь, я хочу добавлять еду за прошлые дату/время, чтобы закрывать пропуски. *Вне MVP.*

### US-015 — Новые каналы, фото и голос · **Won't (now)**
Как пользователь, я хочу пользоваться через сайт/мини-апп ВК и вводить еду фото или голосом. *Дальнейшее развитие.*

### US-016 — Локальная копия БД OFF · **Won't (now)**
Как владелец системы, я хочу локальную копию OpenFoodFacts для скорости и независимости от лимитов. *Будущее.*

## 9. Допущения (Assumptions) — проверить при валидации

- **A1.** Часовой пояс хранится per-user; по умолчанию МСК; смена TZ — после MVP.
- **A2.** Логирование только в текущий день/«сейчас»; запись задним числом — после MVP.
- **A3.** Язык интерфейса и ввода — только русский.
- **A4.** Каналы помимо Telegram, фото и голос — вне MVP; модель данных учитывает мульти-канальность на будущее, но привязка не реализуется.
- **A5.** Идентификация в MVP неявная по Telegram user_id; отдельной авторизации/пароля нет.
- **A6.** Если за прошедший день записей не было — авто-сводка в 9:00 **не отправляется**. *(Принятое решение, не требует подтверждения.)*
- **A7.** Подтверждение распознанного — **per-user настройка** (каждый пользователь включает/выключает сам). По умолчанию **выключено** (автоматическая запись). Автор может изменить дефолт.
- **A8.** Содержимое дневной сводки = список позиций за день + суммарный итог КБЖУ; без графиков и трендов. Ответ на сообщение про еду (US-002) — отдельный формат (разбивка по продуктам + КБЖУ/100 г + источник + итог по съеденному).
- **A9.** Источник КБЖУ **для каждого отдельного продукта один** (OFF либо LLM) — смешивания внутри одного продукта нет. Но **разные продукты одного сообщения/записи могут иметь разные источники** (смешивание допустимо на уровне ввода).
- **A10.** Признак **«пользователь-разработчик»** — per-user. Для dev-пользователей у записей виден идентификатор, по которому идёт удаление (US-009). Для обычных пользователей упрощённый UX удаления — после MVP.
- **A11.** Частичный разбор: если сообщение «про еду» — разбираем все различимые продукты и считаем по ним КБЖУ (LLM-fallback гарантирует значения по каждому продукту). Если не извлекается ни одного осмысленного продукта — трактуем как «не про еду» / просим переформулировать.

## 10. Открытые вопросы (Open Questions)

**Открытых вопросов нет** — все ранее зафиксированные вопросы решены (см. ниже).

### Решённые вопросы

- **Q1 (решён).** Авто-сводка в день без записей — **не отправляется** (см. A6, US-008).
- **Q2 (решён).** Удаление записи — по **видимому идентификатору**, который показывается пользователям-разработчикам (см. A10, US-009). Упрощённый UX для обычных пользователей — после MVP.
- **Q3 (решён).** Источник КБЖУ (OFF/LLM) показывается **в разбивке по продуктам** в ответе (см. US-002); оценочный вес помечается (US-003, US-006).
- **Q4 (решён).** Граница «про еду / не про еду» закрывается явной классификацией намерения каждого сообщения (см. US-017).
- **Q5 (решён).** Частичный разбор: разбираем все различимые продукты; если ничего осмысленного не извлекается — трактуем как «не про еду» / просим переформулировать (см. A11, US-017).

| R1 | **Качество LLM-оценки КБЖУ и веса порций** сильно зависит от промпта; возможны систематические ошибки. | Высокое — прямое искажение учёта. | Промпт — артефакт качества: версионировать, ручная оценка на выборке (метрики разд. 5), помечать оценочные значения. |
| R2 | **OpenFoodFacts слабо покрывает свободные описания готовых блюд** (база преимущественно штрихкодная/брендовая) → частый fallback на LLM. | Высокое — основной источник часто не срабатывает. | Fallback на LLM обязателен и считается штатным путём, а не исключением; в будущем — локальная копия OFF (US-016). |
| R3 | **Лимиты/бан внешнего источника** при росте обращений. | Среднее. | Глобальная стратегия лимитов (US-010), штатная деградация на LLM. |
| R4 | **Тихие регрессии распознавания** при изменении промптов/моделей. | Среднее. | Тесты ядра вместе с кодом (принцип процесса), ручная выборочная проверка. |
| R5 | **Неоднозначность естественного языка** (порции, синонимы, объёмы). | Среднее. | Per-user подтверждение распознанного (US-005); явная пометка оценочных величин. |
| R6 | **Ошибки классификации намерения** (еда принята за обычное сообщение и наоборот). | Среднее — пропуски записей или ложные ответы. | Метрика точности классификации (разд. 5); ручная выборочная проверка; per-user подтверждение для контроля. |
