# Конвенции кода и Definition of Done — Calorithm (ЧИСТОВИК)

> Статус: чистовик, шаг 2 процесса (`docs/development-workflow.md`). Согласовано с принципами процесса и архитектурой (`docs/architecture.md`, `docs/adr/`).
> Назначение: сделать ревью объективным, а работу агентов — предсказуемой (workflow п.6). Язык: русский. Дата: 2026-06-02.

---

## 1. Стек и язык

Python · FastAPI · PostgreSQL · aiogram · LiteLLM · Redis · Docker · **Alembic** (миграции схемы БД — ADR-0014). Конкретные версии фиксируются в lock-файле на старте реализации (свобода реализации в выборе минорных версий).

Базовые требования:
- Полная **типизация** (type hints везде), проверка типобезопасности в CI (напр. mypy/pyright — выбор на этапе реализации).
- **Pydantic** для всех границ (HTTP, события брокера, конфиг).
- Форматирование/линт — единый автоформаттер + линтер (напр. ruff + black-совместимый стиль); правила в конфиге репозитория, прогон в CI.

## 2. Структура проекта и модулей

Один репозиторий. Деплой-юниты (`channel-telegram`, `core-api`, `core-worker`, `diary-worker`, `scheduler`) собирают свои образы, переиспользуя общий код ядра.

Ориентир структуры (свобода в деталях, инварианты — ниже):

```
calorithm/
  core/
    users/         # модуль-владелец схемы users
    diary/         # модуль-владелец схемы diary (вкл. summary_dispatch)
    scheduler/     # stateless триггер 9:00 (без своей схемы — ADR-0013)
    intent/        # stateless
    parsing/       # stateless
    nutrition/     # stateless (+опц. кеш)
    off_client/    # OFF + OFF-лимитер
    llm/           # LiteLLM + LLM-лимитер (единственная точка LLM)
    bus/           # порт MessageBus + адаптеры (Redis/InMemory)
    config/        # Pydantic Settings
    contracts/     # общие DTO/события (Pydantic) — публичные типы границ
  apps/
    core_api/      # FastAPI-приложение (core-api)
    core_worker/   # LLM-only потребитель tasks.llm (ADR-0013)
    diary_worker/  # non-LLM потребитель tasks.diary: генерация/доставка сводок (ADR-0013)
    scheduler/     # лёгкий триггер периодических работ (enqueue build_summary в 9:00)
    channel_telegram/  # адаптер aiogram
  migrations/      # ревизии Alembic (изменения схемы БД — ADR-0014)
  tests/
  docs/
```

Каждый модуль внутри: `service.py` (логика), `repository.py` (доступ к своей схеме, только у модулей с БД), `models.py`/в `contracts` (публичные DTO), `events.py` (публикуемые события).

## 3. Правила развязки модулей и владения схемами (ADR-0001 — обязательно)

1. **Одна схема БД — один владелец-модуль.** Схемы `users`, `diary` принадлежат одноимённым модулям (`summary_dispatch` — в схеме `diary`). Модуль `scheduler` — stateless-триггер без своей схемы (ADR-0013).
2. **Запрет кросс-схемного доступа.** Модуль НЕ читает/пишет чужую схему, НЕ импортирует чужой `repository`, нет кросс-схемных FK.
3. **Межмодульное общение — только через `bus`** (события) или через публичный сервисный интерфейс модуля с типизированными DTO. Не через общие таблицы.
4. **Зависимости — через `contracts`** (Pydantic DTO/события), не через импорт чужих внутренностей.
5. **Цель — механический вынос:** любой модуль должен поддаваться выносу в отдельный сервис заменой in-process вызова на HTTP/событие без переписывания логики. Если код это нарушает — это дефект развязки и блокирует ревью.
6. **LLM и OFF — единственные точки.** Любой LLM-вызов — через модуль `llm` (с проходом через LLM-лимитер); любое обращение к OFF — через `off_client` (с OFF-лимитером). Обход запрещён.

---

## 3a. Миграции схемы БД (ADR-0014 — обязательно)

1. **Любое изменение схемы — только через миграцию Alembic.** Ручные `ALTER`/`CREATE`/`DROP` в проде запрещены.
2. **Каждое изменение схемы = ревизия Alembic в репозитории** (каталог `migrations/`); применяется только прогоном миграций (в т.ч. при деплое compose, one-shot до старта сервисов).
3. **Ревизии обратимы**: каждая имеет рабочий `downgrade`; технически необратимые шаги (напр. drop column с данными) — явно отмечаются и обосновываются в ревью.
4. **Развязка схем сохраняется** (ADR-0001): ревизии не вводят кросс-схемных FK; миграция меняет только схему своего модуля-владельца.
5. **Миграция применяется на чистой БД** и проверяется в CI (up→down→up).

---

## 4. Стиль async

- Везде на горячем пути — **`async`/`await`** (FastAPI, aiogram, redis-клиент, HTTP-клиенты, драйвер Postgres async).
- **Не блокировать event loop**: никаких синхронных сетевых/файловых вызовов в async-коде; CPU-тяжёлое — выносить (в MVP не ожидается).
- **Конкурентность воркера** управляется конфигом `K` (asyncio-семафор/набор задач), не хардкодом (ADR-0005).
- **Backpressure** — естественный через `acquire()` лимитера и глубину очереди; не выбрасывать задачи при перегрузе.
- **Идемпотентность handler'ов** обязательна (at-least-once): повторная доставка не создаёт побочных эффектов дважды (ключ — `task_id`/`event_id`).

---

## 5. Обработка ошибок, таймауты, ретраи

- **Таймауты явные** на всех внешних вызовах (LLM, OFF, БД, Redis). Без бесконечных ожиданий.
- **Ретраи с backoff** — для идемпотентных внешних вызовов; число попыток и стратегия — конфиг. На `429`/исчерпание лимита LLM — ждать через лимитер, не «долбить».
- **Graceful degradation:** OFF недоступен/лимит исчерпан → fallback на LLM (US-010). LLM-fallback гарантирует значение по каждому продукту (US-004).
- **Ошибки обработки задачи:** при невосстановимой ошибке публиковать `Result{kind="error", retryable=false}` в канал-источник (пользователь не остаётся без ответа); при восстановимой — оставить в PEL для повторной доставки (at-least-once).
- **Структурированные ошибки HTTP:** единый JSON-формат (`code`, `message`, опц. `details`); не отдавать стектрейсы наружу.
- **Без проглатывания исключений:** ошибки логируются с контекстом (`task_id`, `user_id`, модуль) и отражаются в метриках.

---

## 6. Конфигурация и секреты

- **Pydantic Settings из ENV** — модуль `config` единственный источник истины; модули получают настройки инъекцией, не читают ENV напрямую.
- Секреты: `TELEGRAM_BOT_TOKEN`, `LLM_*` (токен/провайдер/модель + RPM/TPM), `DATABASE_URL`, `REDIS_URL`, `OFF_*`.
- В репозитории — только `.env.example`; реальный `.env` — в `.gitignore`. Прод — ENV контейнеров / secrets VPS.
- **Секреты не логируются и не попадают в метрики/трассировки.** Промпты версионируются как артефакт качества (R1, R4) — хранятся в коде/файлах под ревью, с указанием версии в метриках LLM.

---

## 7. Требования к метрикам и логам

- **Метрики (Prometheus) — часть фичи, не «потом»** (ADR-0010). Каждый сервис экспонирует `/metrics`. Новый код на горячем пути добавляет релевантные метрики из набора §8 архитектуры (LLM, очередь, лимитеры, качество, доставка).
- **Логи структурированные** (JSON или key-value), с корреляцией по `task_id`/`event_id`/`user_id`. Уровни осмысленные; без шума на happy-path в проде.
- **Качество распознавания** (intent/parsing/источник КБЖУ) отражается в метриках — это основной сигнал тихих регрессий ядра (workflow принцип 1, R4).

---

## 8. Тестирование

- **TDD: тесты пишутся ДО реализации** (workflow принцип 1). Порядок среза: тесты к запланированному функционалу (сначала красные) → валидация автором глазами → реализация под зелёное. Тесты — спецификация намерения; к каждому тесту лаконичный, но понятный комментарий (что и зачем проверяется).
- **Уровни:**
  - юнит — логика модулей, парсинг ответов LLM, расчёт КБЖУ, лимитеры;
  - интеграция — через `InMemoryBus` (без поднятого брокера) для пайплайна и доставки; репозитории — против тестовой БД;
  - контрактные — соответствие DTO/событий схемам из `docs/contracts.md`.
- **LLM/OFF — мокируются** в тестах (детерминизм); реальные вызовы — вне обычного прогона.
- **Идемпотентность и at-least-once** покрываются тестом (повторная доставка `Task` не создаёт дубль записи).
- **Ядро ломается тихо** → особое внимание к регрессионным тестам парсинга/классификации на фиксированных примерах.

## 9. Definition of Done

Задача (срез) считается готовой, когда выполнено ВСЁ нижеперечисленное (согласовано с workflow шаги 6–9):

1. **Код реализует acceptance-критерии** соответствующей US из `prd.md`; границы — типизированные Pydantic DTO (`contracts`).
2. **Тесты написаны ДО кода (TDD)**, провалидированы автором глазами и проходят (red→green): юнит + релевантные интеграционные/контрактные; покрыты идемпотентность и пути деградации (если применимо). К каждому тесту — лаконичный понятный комментарий.
3. **Развязка соблюдена** (раздел 3): нет кросс-схемного доступа, LLM/OFF — только через свои модули, межмодульное — через `bus`/DTO.
4. **Метрики и логи добавлены** для нового поведения на горячем пути (раздел 7); `/metrics` валиден.
5. **Конфигурация/секреты** — через `config`; новые параметры отражены в `.env.example`; секреты не утекают в логи/метрики.
6. **Линт, формат и типобезопасность** проходят в CI.
7. **Ревью пройдено** (`code-reviewer`); комментарии закрыты (workflow шаги 7–8).
8. **Security-пасс** (`security-auditor`) пройден, **если срез трогает секреты, пользовательский ввод или инфраструктуру** (workflow принцип 2, шаг 7). Пользовательский ввод и LLM-границы — типичные триггеры.
9. **Изменения схемы БД — через миграцию Alembic** (ADR-0014, раздел 3a): ревизия приложена, обратима (рабочий `downgrade`) и применяется на чистой БД; ручных `ALTER` в проде нет.
10. **Документация обновлена** при изменении контрактов/архитектуры/решений: `docs/contracts.md`, `docs/architecture.md`, при необходимости новый/обновлённый ADR; промпты версионированы.
11. **Проект остаётся деплоибельным** (workflow принцип 3): docker-compose поднимается, скелет сквозного пути не сломан.

> Закрытие стадии (workflow шаг 9) дополнительно требует: интеграционная проверка, security-пасс по стадии, обновление CHANGELOG, ручная валидация автором перед пушем/тегом.
