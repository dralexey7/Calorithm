# Calorithm — Процесс разработки

Согласованный план работы над продуктом. Ему следуем во всех сессиях.

**Продукт:** умный счётчик калорий в Telegram. Пользователь пишет в свободной форме о съеденном
("грамм 200 жареной курицы с гречкой", "тарелка куриного супа"); система парсит текст в
структурированный вид, получает КБЖУ, сохраняет и даёт отслеживать потребление.

**Подтверждённый стек:** Python · FastAPI · PostgreSQL · Telegram (aiogram) · LiteLLM · Docker.

## Принципы, на которых стоит процесс

1. **Тесты пишутся вместе с кодом**, а не «потом». Ядро (LLM-парсинг свободного текста) ломается тихо — без тестов регрессии незаметны.
2. **Безопасность — часть цикла.** `security-auditor` гоняется перед пушем стадий, которые трогают секреты, пользовательский ввод или инфраструктуру.
3. **Деплой стоит с самого начала**, а не в конце. Проект держим деплоибельным постоянно, чтобы не собрать все грабли инфры в один день на финале.
4. **Шагающий скелет до фич.** Сначала тончайший сквозной путь, потом фичи вертикальными срезами поверх рабочего скелета.
5. **Стадия — это веха из нескольких задач.** Внутренний цикл «реализация→ревью→правка» крутится по срезам/задачам; стадия закрывается интеграционной проверкой.
6. **Конвенции зафиксированы письменно** (кодстайл + Definition of Done) — иначе ревью субъективно, а агенты неэффективны.

## Точки ручной валидации

Автор проекта валидирует руками: **шаги 1–5** и **закрытие стадии (шаг 9) перед пушем**.

Тончайший сквозной путь (*сообщение → backend → БД-заглушка → ответ*) + Docker + БД + **рабочий деплой**.
Цель — не фичи, а доказать, что всё соединяется и катится в прод.
