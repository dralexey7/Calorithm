# Calorithm — Процесс разработки

Согласованный план работы над продуктом. Ему следуем во всех сессиях.

**Продукт:** умный счётчик калорий в Telegram. Пользователь пишет в свободной форме о съеденном
("грамм 200 жареной курицы с гречкой", "тарелка куриного супа"); система парсит текст в
структурированный вид, получает КБЖУ, сохраняет и даёт отслеживать потребление.

**Подтверждённый стек:** Python · FastAPI · PostgreSQL · Telegram (aiogram) · LiteLLM · Redis · Alembic · Docker · Prometheus + Grafana.
Детали — `docs/architecture.md`, `docs/contracts.md`, `docs/conventions.md`, `docs/adr/`.

## Принципы, на которых стоит процесс

1. **TDD: тесты пишутся ДО кода.** На каждой итерации цикла, после проработки плана среза, сначала пишутся тесты к запланированному функционалу (их валидирует автор глазами — нужны лаконичные, но понятные комментарии к каждому тесту), и только потом — реализация, которая подгоняется под тесты (red → green). Ядро (LLM-парсинг свободного текста) ломается тихо — тесты-спецификация ловят регрессии и фиксируют намерение до кода.
2. **Безопасность — часть цикла.** `security-auditor` гоняется перед пушем стадий, которые трогают секреты, пользовательский ввод или инфраструктуру.
3. **Деплой стоит с самого начала**, а не в конце. Проект держим деплоибельным постоянно, чтобы не собрать все грабли инфры в один день на финале.
4. **Шагающий скелет до фич.** Сначала тончайший сквозной путь, потом фичи вертикальными срезами поверх рабочего скелета.
5. **Стадия — это веха из нескольких задач.** Внутренний TDD-цикл «тесты→реализация→ревью→правка» крутится по срезам/задачам; стадия закрывается интеграционной проверкой.
6. **Конвенции зафиксированы письменно** (`docs/conventions.md`: кодстайл + Definition of Done) — иначе ревью субъективно, а агенты неэффективны.

## Точки ручной валидации

Автор проекта валидирует руками: **шаги 1–5**, **тесты каждого среза (шаг 6)** и **закрытие стадии (шаг 10) перед пушем**.

### Фаза 1 — Шагающий скелет

Тончайший сквозной путь (*сообщение → backend → БД-заглушка → ответ*) + Docker + БД + **рабочий деплой**.
Цель — не фичи, а доказать, что всё соединяется и катится в прод. Делается тем же TDD-циклом (Фазы 2…N).

## Петли назад

- Если на шаге 6 написание тестов вскрывает пробел/противоречие в плане — возврат к шагу 5 (а при проблеме требований — к шагу 1).
- Ревью (8) или интеграция (10) могут вскрыть проблему архитектуры — тогда возврат к шагу 2 или 5.
- Фаза 0 не «отлита в граните»: уточняется по мере того, как требования становятся конкретнее.
