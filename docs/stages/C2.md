## 1. Цель стадии

Поднять **async-петлю обработки на брокере, в режиме echo**, без реальной бизнес-логики, доказуемо деплоибельную. Конкретно: ввести **Redis** в compose (внутренняя сеть, не наружу, healthcheck) + порт **`MessageBus`** с адаптерами **Redis Streams** и **InMemory** (для тестов) + минимальные DTO **`ProcessingTask`/`ProcessingResult`/`Result`** в `core/contracts` + новый деплой-юнит **`processing-worker`** (stateless, БЕЗ БД, заглушка-echo пайплайна) + дополнения **`api-core`** (эндпоинт `POST /v1/messages`, реально публикующий задачу; consumer-loop по `results.processing`, публикующий итоговый `Result` в `results.<channel>`).

Доказать, что петля

```
POST /v1/messages → tasks.processing → processing-worker (echo) → results.processing → api-core → results.<channel>
```

работает (тестами через InMemoryBus и интеграционно через реальный Redis), идемпотентна при повторной доставке (at-least-once), и весь compose (`postgres` + `redis` + `migrate` + `api-core` + `processing-worker`) поднимается одной командой.

**Цель — каркас async-петли, не фичи.** Воркер только echo-ретранслирует входной текст; persist в БД нет; реальный резолв пользователя нет; LLM/OFF/парсинга нет.

## 2. Рамки стадии

### Входит (С2)

- **`core/bus`**: порт `MessageBus` (Protocol по `contracts.md` §4) с семантикой at-least-once + идемпотентный handler + явный ack; адаптер `RedisStreamsBus` (consumer groups, ack после успешной обработки, повторная доставка из PEL при ошибке); адаптер `InMemoryBus` (для тестов без брокера). ADR-0004.
- **`core/contracts`**: минимальные Pydantic DTO `ProcessingTask`, `ProcessingResult`, `Result` (+ вспомогательные `ReplyTo`; envelope-поля `schema_version`/`event_id`/`occurred_at`), достаточные для echo-петли. `user_id` — **целочисленный (`int`/bigint)** согласно `data-model.md` §1.
- **`apps/processing_worker`** — новый деплой-юнит, stateless, **без БД** (ADR-0015): подписан на `tasks.processing` (consumer group `processing-workers`), возвращает `ProcessingResult` (echo: `intent="food"`, текст обратно) в `results.processing`. Заглушка пайплайна — без LLM/OFF/парсинга. `/healthz`, `/metrics`. Идемпотентный handler по `task_id`.
- **`apps/api_core`** — дополнения:
  - **`POST /v1/messages`** (`IngestMessageRequest` → `IngestMessageResponse{task_id, status="queued"}`): валидирует, формирует `ProcessingTask{kind="ingest_message"}`, публикует в `tasks.processing`, отвечает сразу. **Резолв `user_id` — заглушка** (см. §8, Q-C2-3).
  - **consumer-loop** по `results.processing` (consumer group `api-core-orchestrator`): принимает `ProcessingResult`, формирует `Result{kind="logged"|"not_food"}` (echo, **без persist**), публикует в `results.<channel>` (в MVP `results.telegram`). `api-core` — **единственный публикатор** `results.<channel>` (ADR-0008/0015).
  - Совмещение HTTP-сервера и consumer-loop в одном процессе (lifespan-управляемая asyncio-задача — см. §8, Q-C2-1).
- **`core/config`**: добавить `REDIS_URL` (Pydantic Settings; единственный источник истины §6) + `.env.example`.
- **docker-compose**: сервис `redis` (внутренняя сеть, не публикуется наружу, healthcheck) + сервис `processing-worker`. `api-core` теперь зависит и от `redis`.
- **Метрики/логи**: базовые метрики очереди/доставки (§7 архитектуры) на горячем пути; корреляция логов по `task_id` сквозь `api-core → worker → api-core` (трассируемость §1b roadmap, ADR-0017).
- **Реконсиляция контрактов**: `docs/contracts.md` местами указывает `user_id: UUID` — привести к `bigint`/`int` (мелкая правка контрактов, DoD §10) — см. C2-T07.

### НЕ входит (отложено)

- **`channel-telegram` адаптер и реальная доставка пользователю** — **С3**. В С2 петля проверяется на уровне шины/тестов (подписчик `results.telegram` в тесте читает опубликованный `Result`), без реального TG.
- **Реальная классификация/парсинг/КБЖУ (LLM/OFF)** — С7+. В С2 воркер только echo; модули `intent`/`parsing`/`nutrition`/`llm`/`off_client` **не создаются**.
- **Персист записей `entries`/`entry_items` в БД** — **С11**. **Подтверждаю:** в С2 БД-таблиц для записей ещё нет (миграция `0001` создала только схемы `users`/`diary`, без таблиц — `data-model.md` §7). Echo **ничего не персистит**; consumer-loop `api-core` НЕ касается БД на этой стадии (это зерно оркестрации, persist встроит С11). Воркер БД не касается никогда (ADR-0015).
- **Резолв пользователя/настройки** — **С6**. В С2 `user_id`/`channel` берутся из запроса как есть; реальный резолв — заглушка (см. §8, Q-C2-3). Минимальное решение зафиксировано там же.
- **`scheduler`, persist-оркестрация-заглушка, `/v1/internal/auto-summary`** — **С4** (consumer-loop С2 — зерно, которое С4 расширит).
- **Prometheus/Grafana/экспортёры** — С5 (С2 лишь *экспонирует* `/metrics` на воркере; скрейпер не поднимается).
- **Новые миграции/таблицы** — нет (С2 не трогает схему — `data-model.md` §7).

### C2-T01 — `core/contracts` (DTO)

### C2-T02 — `InMemoryBus`
- `test_inmemory_bus.py`:
  - `publish(topic, event)` + `subscribe(topic, group, handler)` — handler получает опубликованное событие. *(базовая семантика порта `MessageBus` — `contracts.md` §4)*
  - **ack после успешной обработки**: успешно обработанное событие не доставляется повторно. *(явный ack — §4 контракта, §4 conventions)*
  - **at-least-once при ошибке handler'а**: если handler бросает до ack, событие доставляется повторно (не теряется). *(at-least-once — §4 контракта; основа идемпотентности)*
  - две подписки в **разных** группах получают событие каждая (fan-out по группам). *(семантика consumer groups, переносимая на Redis)*
  - **[ТДЕ-2] две подписки в ОДНОЙ группе**: событие доставляется ровно одному из двух handler'ов (competing consumers — не обоим). *(семантика load-balancing внутри группы; перенос с Redis Streams на InMemory)*
  - **[ТДЕ-3] `publish` топика без подписчиков** не вызывает исключения. *(устойчивость к лишним событиям — порт не должен падать на publish-только)*
- *Комментарий-ориентир:* «InMemoryBus честно эмулирует at-least-once + ack — на нём строится весь основной контур тестов без брокера».

### C2-T03 — `RedisStreamsBus` (реальный Redis)
- `test_redis_bus.py` (`@pytest.mark.integration`, testcontainers Redis):
  - publish → subscribe через реальный stream: событие доезжает до handler'а в нужной consumer group. *(адаптер Redis Streams реализует порт — ADR-0004)*
  - **XACK после успеха**: подтверждённое сообщение уходит из PEL (Pending Entries List). *(ack снимает запись из PEL — корректный at-least-once)*
  - **повторная доставка из PEL**: при ошибке handler'а (без ack) сообщение остаётся в PEL и переедет повторно. *(at-least-once на реальном брокере; не теряем при сбое)*
  - явный таймаут на чтение/подключение — нет бесконечного ожидания. *(таймауты на внешних вызовах — conventions §5)*
  - **[ТДЕ-4] fan-out по разным consumer groups на реальном Redis**: два разных `group` подписаны на один топик — оба получают сообщение независимо. *(зеркальный тест InMemoryBus fan-out на реальном адаптере — взаимозаменяемость ADR-0004)*
- *Комментарий-ориентир:* «тот же контракт `MessageBus`, что у InMemoryBus, выполняется на реальном Redis — адаптер взаимозаменяем».

### C2-T04 — `processing-worker` (заглушка-echo)
- `test_worker_pipeline.py` (юнит, без брокера):
  - заглушка пайплайна на `ProcessingTask{kind=ingest_message, text}` возвращает `ProcessingResult{task_id (тот же), intent="food", items=None|echo, …}` — echo, без LLM/OFF. *(пайплайн — заглушка; реальная логика С7+)*
  - `task_id` протягивается из `Task` в `Result` без изменения. *(трассируемость §1b roadmap, ADR-0017; корреляция сохраняется)*
  - **идемпотентность handler'а по `task_id`**: повторная обработка той же задачи не порождает второй разный результат / двойного эффекта. *(идемпотентный handler — §4 conventions)*
- (через InMemoryBus, интеграционно) воркер, подписанный на `tasks.processing`, кладёт `ProcessingResult` в `results.processing`. *(роль воркера в петле; без БД — ADR-0015)*
- **[ТДЕ-5] `processing_worker` не импортирует драйвер БД**: статическая проверка — `import apps.processing_worker` не тянет `asyncpg`, `sqlalchemy`, ни один ORM/репозиторий. Реализуется инспекцией `sys.modules` после импорта. *(ADR-0015 — воркер БД не касается; дефект развязки блокирует ревью conventions §3.7)*
- `test_worker_health.py` — **health/readiness нового сервиса**:
  - `GET /healthz` воркера → `200` при доступном **брокере (Redis)**; `503` при недоступном. Воркер зависит от брокера, не от БД, поэтому проба — брокерная. Юнит — мок пробы через override; интеграция — реальный Redis (testcontainers) для `200` и недостижимый `REDIS_URL` для `503` (по образцу C1 healthz). *(readiness честно отражает реальную зависимость воркера; conventions §5; тело `503` — JSON без трейсов)*
  - `GET /metrics` воркера → `200`, валидный Prometheus-формат. *(метрики воркера с самого начала — ADR-0010/§7)*
- *Комментарий-ориентир:* «воркер БД не касается, только считает (echo) и возвращает результат в `results.processing`; его healthz проверяет брокер».

### C2-T05 — `POST /v1/messages` (публикация задачи)
- `test_messages_endpoint.py` (ASGI-клиент + InMemoryBus через DI-override):
  - `POST /v1/messages` с валидным телом → `200` (или `202`) и `{task_id, status="queued"}`; **в `tasks.processing` появилась ровно одна `ProcessingTask`** с тем же `task_id` и текстом. *(тонкая ручка ставит задачу — `contracts.md` §1.2; единственный публикатор `tasks.processing` — `api-core`, ADR-0012)*
  - **[ТДЕ-6] `task_id` в ответе совпадает с `task_id` в опубликованной `ProcessingTask`**: HTTP-ответ и шина несут один и тот же идентификатор задачи (не регенерируется). *(корреляция сквозь границы — ADR-0017; ключ идемпотентности must быть стабилен)*
  - невалидное тело (нет `text`/`channel`/`reply_to`) → `422`, тело — структурированный JSON без стектрейсов. *(валидация границы; conventions §5)*
  - `user_id` в задаче проставлен (заглушка-резолв детерминирована — Q-C2-3). *(резолв — заглушка на С2; реальный С6)*
- `test_health.py` (расширение существующего) — **`/healthz` `api-core` теперь отражает и брокер**: `200`, когда доступны И БД, И Redis; `503`, если недоступен любой из них. Существующие health-тесты обновляются: проба брокера — отдельная переопределяемая зависимость (как `get_db_probe`), мок в юнитах; интеграция — реальный Redis. **[ТДЕ-7] Четыре комбинации состояний** покрыты юнит-тестами: (БД ok + брокер ok → 200), (БД ok + брокер fail → 503), (БД fail + брокер ok → 503), (БД fail + брокер fail → 503). *(исчерпывающее покрытие комбинаций зависимостей; conventions §5; api-core зависит от Redis с С2)*
- *Комментарий-ориентир:* «вход в ядро — только HTTP; адаптер задачи в брокер не публикует (ADR-0012); ручка кладёт `ProcessingTask` и сразу отвечает `queued`; healthz api-core стал учитывать брокер».

### C2-T06 — consumer-loop `api-core` (results.processing → results.<channel>)
- (интеграционно, InMemoryBus) `test_echo_loop_inmemory.py` — **сквозная петля без TG**:
  - публикуем `ProcessingTask` в `tasks.processing` → воркер-handler кладёт `ProcessingResult` в `results.processing` → consumer-loop `api-core` публикует `Result{kind=logged}` в `results.telegram`; тестовый подписчик `results.telegram` получает `Result` с тем же `task_id`/`reply_to`/`channel`. *(полная петля §4.2 архитектуры доказана на шине; персиста нет — С11)*
  - `intent="not_food"` в `ProcessingResult` → `Result{kind="not_food"}` (ветка не-еды echo). *(маппинг результата воркера в результат канала; persist не нужен)*
  - consumer-loop **не обращается к БД** на С2. *(зерно оркестрации без persist; persist встроит С11 — ADR-0015)*
  - **`api-core` — единственный публикатор `results.<channel>`**: воркер в `results.telegram` не публикует. *(ADR-0008/0015 — проверяется тем, что в `results.telegram` пишет только consumer-loop)*
  - **[ТДЕ-8] consumer-loop не падает при ошибке handler'а**: если handler оркестратора бросает исключение для одного `ProcessingResult`, цикл продолжает обрабатывать следующий (изоляция ошибок, Q-C2-1). *(loop не может ронять HTTP-сервер; conventions §5)*
- `test_idempotency.py` — **at-least-once / идемпотентность (обязательный тест)**:
  - **повторная доставка `ProcessingTask`** (один `task_id` дважды) → echo-петля даёт **один** итоговый `Result` в `results.telegram` (или повтор не создаёт второго эффекта). *(идемпотентность по `task_id`; at-least-once не двоит — §4 conventions, DoD §2)*
  - **повторная доставка `ProcessingResult`** (один `task_id` дважды в `results.processing`) → consumer-loop не публикует второй `Result`. *(dedup по `task_id` на стороне оркестратора без БД — Q-C2-4)*
- *Комментарий-ориентир:* «повторная доставка `Task`/`Result` не двоит итог — идемпотентность по `task_id`; это ядро гарантии at-least-once до появления persist в С11».

### C2-T08 — compose + деплоибельность
- Проверяется **поднятием compose** (интеграционная проверка среза, не обязательно pytest):
  - `docker compose up` поднимает `postgres` → `redis` (healthcheck зелёный) → one-shot `migrate` → `api-core` + `processing-worker`; все `/healthz`/`/metrics` зелёные. *(сквозная деплоибельность одной командой — DoD §11)*
  - **порт Redis не опубликован наружу** (только внутренняя сеть `calorithm_net`). *(инфра-безопасность; брокер внутренний — §9 архитектуры)*
  - сервис **`processing-worker` имеет compose-healthcheck** на свой `/healthz` (как `api-core` с С1); неживой сервис рестартуется/виден. *(оркестрация здоровья новых сервисов — DoD §11)*
  - echo-петля проходит против поднятого compose (ручной `curl POST /v1/messages` → результат виден в `results.telegram` через лог/тестовый подписчик). *(петля работает в собранном виде)*
- *Комментарий-ориентир:* «compose со всеми сервисами стадии поднимается одной командой; Redis внутренний; петля катится».

### C2-T09 — CI
- CI-джоб гоняет юнит + интеграцию (Redis-testcontainers и InMemory); линт/тип/формат зелёные; гейт миграций `up→down→up` сохранён (схема С2 не меняется, но регресс ловим). *(гейты §6 DoD; защита от регресса)*

## 6. Критерии завершения стадии (exit criteria)

Со ссылкой на Definition of Done (`conventions.md` §9) и exit-критерий Стадии 2 roadmap:

- [ ] **Тесты написаны до кода (TDD), провалидированы автором глазами, зелёные** (DoD §2): контракты (DTO, `user_id: int`, envelope), `InMemoryBus` (publish/subscribe/ack/at-least-once), `RedisStreamsBus` (реальный Redis), воркер-echo, `POST /v1/messages` (публикация задачи), consumer-loop (петля + маппинг), **идемпотентность повторной доставки `Task`/`Result`**.

- [ ] **Метрики и логи** (DoD §4, §7): воркер и `api-core` экспонируют валидный `/metrics`; базовые метрики очереди/доставки добавлены на горячем пути; логи коррелируют по `task_id` сквозь `api-core → worker → api-core` (трассируемость §1b, ADR-0017).

- [ ] **Линт, формат и типобезопасность проходят в CI** (DoD §6); гейт миграций `up→down→up` сохранён (DoD §9, хотя схема не меняется).
- [ ] **Docker-compose поднимается одной командой** (`postgres` + `redis` + `migrate` + `api-core` + `processing-worker`); **Redis внутренний (порт не публикуется), healthcheck зелёный**; проект деплоибелен локально и на VPS (DoD §11).
- [ ] **Контракты синхронны** (DoD §10): `docs/contracts.md` приведён к `user_id: bigint/int` (снят дрейф UUID); новые DTO отражены.

## 8. Открытые вопросы реализации

- **Q-C2-1 (совмещение HTTP-сервера и consumer-loop в `api-core`).** `api-core` должен одновременно обслуживать HTTP и потреблять `results.processing`. **Предложение плана:** запускать consumer-loop как **asyncio-задачу через FastAPI lifespan** (старт при старте приложения, graceful cancel при остановке) в том же процессе — не отдельный деплой-юнит (ADR-0015 допускает совмещение web-фасада и оркестратора, делится позже без изменения контрактов). Альтернатива (отдельный процесс-оркестратор) — избыточна для С2. *Помечено «свобода реализации»; зафиксировать на C2-T06.* Внимание: задача consumer-loop не должна ронять HTTP-сервер при ошибке handler'а (изоляция + рестарт цикла; ошибки — в метрики/логи, §5).
- **Q-C2-2 (формат `task_id`).** `contracts.md` фиксирует `task_id: str` (ключ идемпотентности → будущий `entries.source_task_id`). **Предложение:** генерировать в `api-core` при приёме `/v1/messages` (напр. UUID4 в виде строки, или ULID — свобода реализации), стабильный на весь путь. *Помечено «свобода реализации»; зафиксировать на C2-T05.*
- **Q-C2-3 (резолв `user_id` — заглушка на С2).** Реальный резолв — С6 (схема `users` появляется в `0002`). **Минимальное решение для С2:** `api-core` проставляет **детерминированную заглушку** `user_id` (напр. фиксированное число или производное от `channel_user_id` — без обращения к БД), чтобы `ProcessingTask.user_id: int` было заполнено и петля деплоибельна. Echo ничего не персистит, поэтому корректность значения здесь не критична. *Зафиксировать заглушку на C2-T05; пометить TODO-ссылкой на С6.*
- **Q-C2-4 (идемпотентность без БД на С2).** Persist (и `entries.source_task_id UNIQUE`) появляется в С11; на С2 БД для записей нет. **Вопрос:** нужно ли на С2 хранить что-либо для dedup. **Предложение плана:** идемпотентность echo-петли доказывается на уровне **семантики handler'а** (повторная доставка того же `task_id` даёт тот же безэффектный результат — echo по природе идемпотентен) и, при необходимости, **лёгкий dedup по `task_id` в Redis** (SET с TTL) — **только если** тест C2-T06 показывает двоение `Result`. Не вводить тяжёлой инфраструктуры раньше времени: предпочесть естественную идемпотентность echo; Redis-dedup — опционален и минимален. *Решение — на C2-T06 по результату red-теста; «свобода реализации» в пределах «не двоить эффект».*
- **Q-C2-5 (область `Result.payload` на С2 — «свобода реализации»).** `Result{kind=logged}` в полном виде несёт `entry_id`/`items`/`totals` (`contracts.md` §3.2). На С2 нет persist и нет КБЖУ — **echo-`payload` минимален** (напр. исходный текст / пустые items). Полный payload — С11. *Зафиксировать минимальную форму на C2-T01/C2-T06; не плодить лишних полей.*
- **Q-C2-6 (точка внимания, не блокер): provider шины через DI.** Чтобы тесты гоняли InMemoryBus, а прод — Redis, `bus_provider` собирает реализацию из `REDIS_URL`/настроек и инъектируется (DI/override), как `get_db_probe` в С1. *Помечено «свобода реализации»; зафиксировать на C2-T05.*
