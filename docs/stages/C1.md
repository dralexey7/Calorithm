# Стадия С1 — детальный план реализации

> Статус: **черновик, шаг 5 процесса** (`docs/development-workflow.md`). Требует ручной валидации автором перед стартом TDD (шаг 6).
> Источники истины: `docs/roadmap.md` (Стадия 1), `docs/architecture.md`, `docs/contracts.md`, `docs/conventions.md` (§2 структура, §3a миграции, §4 async, §6 конфиг, §7 метрики, §8 тесты, §9 DoD), `docs/data-model.md` (§7 — С1 = `0001` init + `CREATE SCHEMA users, diary`).
> Этот план **не вводит новых архитектурных решений**; держится в рамках принятых ADR-0001/0010/0011/0014/0015.
> Дата: 2026-06-03 · Язык: русский.

---

## 1. Цель стадии

Поднять **доказуемо запускающийся и деплоибельный каркас** ядра БД/API: репозиторий по структуре конвенций + модуль `config` (Pydantic Settings) + Postgres в compose + инициализация Alembic + миграция `0001` (init + `CREATE SCHEMA users, diary`, baseline без бизнес-таблиц) + `api-core` (FastAPI) с `/healthz` и `/metrics` + базовый тулинг (линт/формат/типы/тесты) + деплоибельный docker-compose (минимум `api-core` + `postgres` + one-shot миграции) + `.env.example`.

**Цель — каркас, не фичи.** Доказать, что инфраструктура соединяется (`api-core` ↔ Postgres), миграции применяются и обратимы, сервис живой (`/healthz`/`/metrics`), и всё это катится в прод одной командой.

## 2. Рамки стадии

### Входит (С1)
- Скелет репозитория: структура каталогов `core/`, `apps/`, `migrations/`, `tests/`, `docs/` (conventions §2).
- Тулинг: автоформаттер + линтер + типчекер + тест-раннер; прогон в CI (DoD §6).
- Модуль `core/config` — Pydantic Settings, единственный источник истины по ENV (conventions §6).
- `apps/api_core` — FastAPI-приложение: `GET /healthz` (liveness + проба БД), `GET /metrics` (Prometheus-формат).
- Alembic: инициализация (`alembic.ini`, `migrations/env.py`), миграция `0001` (init + `CREATE SCHEMA users, diary`, baseline без таблиц).
- `docker-compose`: `postgres` + `api-core` + one-shot шаг прогона миграций до старта `api-core`.
- `.env.example` со всеми ENV, нужными на С1; реальный `.env` — в `.gitignore`.
- Runbook запуска: локально и на VPS (README или `docs/`).

### НЕ входит (отложено на С2+)
- **Бизнес-логика и бизнес-таблицы** — нет (таблицы `users`/`diary` появляются в С6/С11; С1 создаёт только схемы).
- **`POST /v1/messages`** и прочие `/v1`-эндпоинты — НЕТ на С1. *(Roadmap §2 упоминал тонкую заглушку `POST /v1/messages` для С1; здесь она сознательно отложена — см. §8, Вопрос Q-C1-1: на С1 нет ни `bus`, ни резолва пользователя, заглушка не доказывает ничего сверх `/healthz`/`/metrics` и тянет каркас `contracts`/DTO раньше времени. Реальная ручка вводится в С2 вместе с шиной.)*
- **Redis / `MessageBus` / очереди** — С2.
- **`processing-worker`, `scheduler`, `channel-telegram`** — С2–С4.
- **Prometheus / Grafana / экспортёры** — С5 (на С1 `api-core` лишь *экспонирует* `/metrics`, но скрейпер не поднимается).
- **LLM / OFF / лимитеры** — С7+.
- **Модули `users`/`diary`** (service/repository) — С6/С11.

## 5. TDD-заметки по срезам (какие тесты пишутся первыми — red)

> Это спецификация намерения для шага 6. К каждому тесту — лаконичный понятный комментарий (что и зачем проверяется), который автор валидирует глазами. LLM/OFF на С1 отсутствуют — мокировать нечего.

### C1-T01 — скелет + тулинг
- Первый «тест» здесь — **прогон тулинга**, а не pytest: линтер/формат/типчекер запускаются и проходят на пустом скелете; CI зелёный.
- `tests/test_smoke.py` (минимальный): импорт пакета не падает — каркас собран корректно.
- *Комментарий-ориентир:* «каркас репозитория импортируется и проходит линт/тип/формат — фундамент готов».

### C1-T02 — `config`
- `test_config.py`:
  - `config` загружает `DATABASE_URL` из ENV. *(конфиг читается из окружения — единственный источник истины §6)*
  - отсутствие обязательной переменной → понятная ошибка валидации (Pydantic), не «тихий» дефолт там, где значение обязательно. *(fail fast при неполном окружении)*
  - секрет (`DATABASE_URL`) не попадает в `repr`/строковое представление настроек. *(секреты не утекают — §6)*
  - все переменные из `.env.example` соответствуют полям модели (нет «осиротевших» ENV). *(`.env.example` полон и синхронен — DoD §5)*

### C1-T03 — миграция `0001`
- `test_migration_0001.py` (против тестовой БД):
  - на **чистой** БД `alembic upgrade head` применяется без ошибок. *(миграция применяется на чистой БД — §3a п.5)*
  - после `upgrade` существуют схемы `users` и `diary`. *(C1-цель data-model §7: создаются обе схемы)*
  - после `upgrade` **бизнес-таблиц нет** (baseline пустой — только схемы). *(С1 не вводит таблиц)*
  - цикл `up → down → up` проходит на чистой БД без ошибок; после `downgrade` схемы убраны (рабочий обратимый `downgrade`). *(обратимость — §3a п.3/п.5)*

### C1-T04 — `api-core` (`/healthz`, `/metrics`)
- `test_health.py` (ASGI-клиент):
  - `GET /healthz` при **доступной** БД → `200` и тело-индикатор `ok`. *(liveness + реальная проба соединения с БД)*
  - `GET /healthz` при **недоступной** БД (мок/подмена соединения на падающее) → не-`200` (напр. `503`). *(healthcheck честно отражает зависимость от БД — основа деплоибельности)*
- `test_metrics.py`:
  - `GET /metrics` → `200`, `Content-Type` Prometheus-формата, тело парсится как Prometheus-экспозиция (есть хотя бы дефолтные метрики процесса). *(метрики — часть каркаса с самого начала, ADR-0010/§7; формат валиден для будущего скрейпа в С5)*

### C1-T05 — compose + деплоибельность
- Проверяется **поднятием compose** (интеграционная проверка среза, не обязательно pytest):
  - `docker compose up` поднимает `postgres` → one-shot миграции применяются → `api-core` стартует и `/healthz` зелёный. *(сквозная деплоибельность одной командой — DoD §11)*
  - повторный `up` на уже мигрированной БД не падает (идемпотентность one-shot прогона миграций). *(рестарт-безопасность деплоя)*
- *Комментарий-ориентир:* «compose поднимается одной командой; миграции применяются до старта api-core; сервис живой».

### C1-T06 — миграции в CI
- CI-джоб поднимает временную БД и прогоняет `up → down → up`, падая при любой ошибке. *(гейт обратимости миграций в CI — §3a п.5; защита от необратимых ревизий на будущих стадиях)*

## 6. Критерии завершения стадии (exit criteria)

Со ссылкой на Definition of Done (`conventions.md` §9):

- [ ] **Тесты написаны до кода (TDD), провалидированы автором глазами, зелёные** (DoD §2): `config`, `/healthz` (ok/fal при БД), `/metrics`, миграция `0001` (применение + up→down→up + наличие схем `users`/`diary` + отсутствие бизнес-таблиц).
- [ ] **Миграция `0001` применяется на чистой БД и обратима** (рабочий `downgrade`); `up→down→up` зелёный в CI (DoD §9, §3a).
- [ ] **Схемы `users` и `diary` создаются** миграцией `0001`; бизнес-таблиц нет (data-model §7).
- [ ] **`/healthz` и `/metrics` живые**: `/healthz` ok при доступной БД и ошибка при недоступной; `/metrics` отдаёт валидный Prometheus-формат (DoD §4).
- [ ] **Конфиг через `config`**; новые ENV отражены в `.env.example`; секреты не утекают в логи/метрики/`repr` (DoD §5, §6).
- [ ] **Линт, формат и типобезопасность проходят в CI** (DoD §6).
- [ ] **Docker-compose поднимается одной командой** (`postgres` + one-shot миграции + `api-core`); проект деплоибелен локально и на VPS (DoD §11).
- [ ] **`.env.example` полон** и синхронен с моделью `config`.
- [ ] **Ревью пройдено** (`code-reviewer`); комментарии закрыты (DoD §7).
- [ ] **Security-пасс пройден** (`security-auditor`) — С1 трогает инфру/секреты (`.env`, `DATABASE_URL`, сеть compose) (DoD §8, roadmap exit С1).
- [ ] **Документация**: README-runbook (локальный запуск + VPS); CHANGELOG обновлён при закрытии стадии (DoD §10 + закрытие стадии).
- [ ] **Проект остаётся деплоибельным**; каркас сквозного пути не сломан (DoD §11).

## 8. Открытые вопросы реализации

- **Q-C1-1 (объём `POST /v1/messages` на С1).** Roadmap §2 («Крупные срезы» С1) упоминал тонкую заглушку `POST /v1/messages` (валидация + `{task_id, status=queued}` без enqueue). **Предложение плана: отложить на С2.** На С1 нет ни `bus`, ни резолва пользователя, ни смысла отдавать `queued` без очереди; заглушка тянет каркас `contracts`/DTO раньше времени и ничего не доказывает сверх `/healthz`/`/metrics`. С2 вводит ручку вместе с реальной публикацией в `tasks.processing`. *Решение за автором на шаге 5.*
- **Q-C1-2 (выбор тулинга — «свобода реализации»).** Конкретные линтер/формат/типчекер не зафиксированы (conventions §1 допускает свободу: напр. ruff + mypy/pyright). **Помечено как свобода реализации**; разработчик фиксирует выбор в `pyproject.toml`/CI на С1-T01. Не требует отдельного решения автора.
- **Q-C1-3 (стратегия healthcheck — «свобода реализации»).** `/healthz` обязан честно отражать доступность БД (проба соединения), но *глубина* пробы (ping vs `SELECT 1`) и формат тела — свобода реализации (contracts §1.8). Зафиксировать на С1-T04; в тесте достаточно проверять ok/не-ok относительно доступности БД.
- **Q-C1-4 (точка внимания, не блокер С1): тип `user_id` в контрактах.** `docs/contracts.md` местами указывает `user_id: UUID`, тогда как `docs/data-model.md` зафиксировал `bigint GENERATED ALWAYS AS IDENTITY` для всех PK. С1 этого не касается (нет ни резолва, ни DTO с `user_id`), но расхождение всплывёт в С2 (`ProcessingTask.user_id`) и С6. **Рекомендация:** привести `contracts.md` к `bigint`/`int` до С2 (отдельной правкой контрактов, DoD §10). Зафиксировано здесь, чтобы не потерять.
