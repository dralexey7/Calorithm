# ADR-0010 — Мониторинг Grafana + Prometheus с самого начала

Статус: принято · Дата: 2026-06-02 · Связано: `architecture.md` §8, `conventions.md` §7

## Context

Ядро (LLM-парсинг) ломается тихо (workflow принцип 1, R4). LLM под одним токеном несёт стоимость и риск 429 (R1, R3). Очередь и лимитеры имеют состояние, за которым нужно следить (глубина, остаток бюджета). Без наблюдаемости с первого дня проблемы видны только постфактум. Откладывать мониторинг «на потом» противоречит принципу «инфра с самого начала» (workflow п.3).

## Decision

**Grafana + Prometheus закладываются с самого начала**, как отдельные деплой-юниты. Каждый сервис (`core-api`, `core-worker`, `channel-telegram`) экспонирует `/metrics` (prometheus_client); Prometheus pull; Redis — redis_exporter; Postgres — postgres_exporter; Grafana — дашборды и алерты. Метрики — часть Definition of Done (`conventions.md` §9).

Минимальный набор: LLM (стоимость/латентность/429/вызовы по назначению), очередь (глубина/возраст/throughput/повторы), лимитеры (остаток бюджета OFF и LLM RPM/TPM, ожидания на acquire), качество (успешность парсинга/классификации, доля OFF vs LLM), доставка (доставлено/ошибки, латентность приём→ответ).

## Consequences

- (+) Тихие регрессии ядра и всплески стоимости/429 видны сразу; есть сигнал для алертов.
- (+) Наблюдаемость очереди и лимитеров — основа для решений о масштабировании (реплики воркера) и миграции брокера (ADR-0004).
- (−) +2 контейнера и обязанность инструментировать новый код метриками (часть DoD).
- (−) Небольшой ресурсный оверхед на одном VPS — приемлемо для отдачи в наблюдаемости.
