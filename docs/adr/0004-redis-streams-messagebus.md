# ADR-0004 — Redis Streams за абстракцией MessageBus (Kafka отложена)

Статус: принято · Дата: 2026-06-02 · Связано: `architecture.md` §2, `contracts.md` §3–§4

## Context

Брокер несёт три роли: очередь обработки (ADR-0003), шина межмодульных событий (ADR-0001), топик доставки результатов (ADR-0008). Масштабируемые лимитеры (OFF, LLM) и так требуют общего состояния вне процесса — естественно это Redis. Рассматривались Kafka, Redis Streams, RabbitMQ, NATS. Реальность: 1–2 пользователя, один VPS, один разработчик. Kafka сразу = тяжёлый JVM-компонент (KRaft/ZooKeeper) ради будущей нагрузки.

## Decision

**Redis Streams сейчас**, скрытый за портом **`MessageBus`** (Protocol). Контракт фиксирует **семантику, а не реализацию**: at-least-once + идемпотентный handler + явный ack. Это общий знаменатель Redis Streams / Kafka / RabbitMQ. Реализации: `RedisStreamsBus` (MVP), `KafkaBus` (позже), `InMemoryBus` (тесты). Модули никогда не импортируют клиент брокера напрямую — только порт.

**Kafka — отложенное, не отменённое решение.** Триггеры миграции (когда, а не если):
- нужен реплей / долгий retention лога событий (event sourcing, аналитика);
- устойчиво >~единиц тысяч событий/сек;
- несколько независимых команд-потребителей одного потока;
- требование строгого ordering на больших объёмах.

Redis также несёт лимитеры и топик результатов.

## Consequences

- (+) Ноль новой инфраструктуры: Redis уже нужен под лимитеры → очередь + consumer groups + ack/PEL без нового процесса.
- (+) Низкий порог входа разработчика; механический путь к Kafka через смену адаптера порта.
- (+) Тесты — на `InMemoryBus`, без поднятого брокера.
- (−) Retention/реплей у Redis Streams слабее Kafka (ограничен `MAXLEN`). В MVP реплей не нужен; появление потребности — явный триггер миграции.
- (−) Партиционирование/шардинг — вручную; до заметных нагрузок не требуется.
