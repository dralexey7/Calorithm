# ADR-0016 — Always-write записей, статусная модель `entry` и мягкое удаление

Статус: принято · Дата: 2026-06-03 · Связано: `architecture.md` §4.2, §6; `contracts.md` §1.4, §3.2; US-002, US-005, US-009, A6, A7; ADR-0015

## Context

Раньше запись еды сохранялась только после подтверждения (при включённом confirm US-005), а удаление (US-009) подразумевало физический `DELETE`. Два недостатка:

- **Потеря данных при confirm-flow и при сбоях:** если запись не подтверждена/прервана, она исчезает, теряются трассируемость и возможность разбора качества парсинга (R4).
- **Жёсткое удаление** необратимо, мешает аудиту и аналитике, и плохо сочетается с at-least-once (повтор задачи на уже удалённой записи).

Нужна модель, где запись **всегда сохраняется**, а её «учётность» в сводках управляется статусом; удаление — мягкое.

## Decision

**1. Always-write.** Запись еды (`entry` + `entry_items`) **сохраняется всегда** при успешной обработке пайплайна — независимо от того, включено ли подтверждение. Persist делает `api-core` (единственный владелец БД, ADR-0015) при получении `ProcessingResult`.

**2. Статусная модель `entry`.** У `entry` есть поле `status` (enum):

| status | Семантика | Учитывается в сводках? |
|---|---|---|
| `pending` | сохранена, ожидает подтверждения (confirm включён, US-005) | нет |
| `confirmed` | подтверждена пользователем, либо confirm выключен (автоподтверждение) | да |
| `rejected` | пользователь отклонил превью (US-005) | нет |
| `deleted` | мягко удалена (US-009) | нет |

Дополнительно — `status_reason: text | null` (напр. `user_rejected`, `user_deleted`, `superseded`) и `status_changed_at: timestamptz` для аудита.

**3. Инвариант сводок.** В дневные сводки (US-007 по запросу, US-008 авто) и в дневные итоги **учитываются только `status='confirmed'`**. Это единственное правило фильтрации; `pending`/`rejected`/`deleted` невидимы в КБЖУ-итогах.

**4. Мягкое удаление (US-009).** Удаление переводит `status` в `deleted` (+`status_reason='user_deleted'`, `status_changed_at`), физический `DELETE` не выполняется. Эндпоинт `DELETE /v1/entries/{id}` идемпотентен: повтор на уже `deleted` возвращает `deleted=true` без ошибки. Только владелец записи; видимый id — для dev (US-009).

**5. Переходы статуса при confirm (US-005):**
- confirm выключен → запись создаётся сразу как `confirmed`.
- confirm включён → запись создаётся как `pending`; подтверждение переводит в `confirmed`, отклонение — в `rejected`. (Превью/подтверждение — деталь реализации confirm-flow, контракт `kind=preview` сохраняется; ADR-0015 §3.)

## Consequences

- (+) Нет потери данных: всё съеденное и распознанное сохраняется, даже если не подтверждено/прервано → трассируемость и разбор качества (R4, ADR-0017).
- (+) Удаление обратимо и аудируемо; идемпотентно при at-least-once.
- (+) Единый понятный инвариант учёта (`confirmed` only) вместо неявной зависимости «есть строка = учтена».
- (−) Сводки и итоги обязаны фильтровать по `status` — легко забыть; выносится в repository-метод модуля `diary` (единая точка), проверяется тестами.
- (−) В таблице накапливаются `rejected`/`deleted` строки — для MVP (1–2 пользователя) незначимо; чистка/архивация — вне scope, обратимо.
- Миграция статуса — ревизией Alembic (ADR-0014), только в схеме `diary`.
