# ADR-0012 — Минимизация синхронных путей и асинхронная сводка по запросу

Статус: принято, **частично изменён ADR-0015** · Дата: 2026-06-02 · Связано: `architecture.md` §4.2, §4.4, §5; `contracts.md` §1.3, §3; ADR-0003, ADR-0008, ADR-0013, ADR-0015

> **Изменён ADR-0015 (2026-06-03):** п.2 (сводка по запросу US-007 — асинхронная) **отменён** — сводка снова **синхронна** в `api-core` (чтение БД + формат, без LLM). В силе остаются: канонический входящий путь сообщения через `core-api`/`api-core` (п.3) и минимизация синхронного как принцип (п.1) — асинхронен только LLM/OFF-пайплайн обработки сообщения. «Минимум синхронного» теперь означает «async там, где есть внешний/медленный/лимитируемый вызов», а не «всё в очередь».


## Context

ADR-0003 ввёл очередь и отложенный ответ для LLM-работы, но часть пользовательских операций оставалась синхронной «в запросе» через `core-api` (в т.ч. сводка по запросу US-007 считалась прямо в HTTP-ответе). Это создаёт разнородные пути доставки (один результат — синхронно из HTTP, другой — асинхронно из топика), усложняет адаптер (он должен и ждать HTTP-ответ, и слушать `results.*`) и плохо переживает всплески: длинный синхронный запрос держит соединение и ресурс. Также в прошлом чистовике входящий путь сообщения был неоднозначен: адаптер мог либо звать `core-api`, либо публиковать `Task` в брокер напрямую.

Принцип процесса — «async где платит» и «минимум синхронного». Нужно зафиксировать, что синхронно, а что нет, и убрать неоднозначность входящего пути.

## Decision

**1. Минимизируем синхронные пути.** Пользовательский запрос по умолчанию **не обрабатывается синхронно «в запросе»**: он ставится в очередь и доставляется через топик результатов (`results.<channel>`), как и приём сообщения о еде. Синхронным остаётся **только то, что обязано** таким быть:

- резолв/регистрация пользователя (`POST /v1/users/resolve`) — нужен до любого enqueue (получить `user_id`);
- чтение/смена настроек (`PATCH /v1/users/settings`) и смена primary-канала (`POST /v1/users/primary-channel`) — мгновенные операции над одной строкой, без тяжёлой работы и без ожидающего «отчёта»;
- сам **enqueue** (`POST /v1/messages`, `GET /v1/summary`, `DELETE /v1/entries/{id}`) — быстрый non-blocking возврат `task_id`/`status=queued`; обработка асинхронна.

Обоснование минимального набора синхронного: это операции, которые либо являются предусловием enqueue (резолв), либо тривиальны и не имеют отложенного результата (настройки/primary), либо сам факт постановки в очередь.

**2. Сводка по запросу (US-007) теперь асинхронна.** `GET /v1/summary` не считает сводку в HTTP-ответе, а ставит задачу `build_summary` в очередь и возвращает `task_id`/`status=queued`. Сводка строится non-LLM обработчиком (`diary-worker`, ADR-0013) и доставляется в канал-источник через `Result{kind="daily_summary"}` в `results.<channel>` — единый путь доставки с приёмом сообщения.

**3. Канонический входящий путь сообщения.** Адаптер канала → `core-api` по HTTP (`POST /v1/messages`), который ставит `Task` в очередь. **Прямой publish `Task` адаптером в брокер убран из контракта.** Адаптер для брокера — только подписчик на `results.*` (ADR-0008). Это чистая версионируемая граница: адаптер не знает имён внутренних топиков задач.

## Consequences

- (+) Единый асинхронный путь доставки результатов (приём, сводка, авто-сводка) → адаптер проще: одна модель «enqueue → жди в `results.*`».
- (+) Нет долгих синхронных HTTP-запросов на тяжёлой работе; всплески сглаживаются очередью.
- (+) Снята неоднозначность входящего пути; граница задач версионируема независимо от адаптеров.
- (−) Сводка по запросу приходит с небольшой задержкой (через очередь), а не мгновенно в HTTP-ответе — приемлемо, ответ всё равно быстрый, очередь сводок не нагружена LLM.
- (−) Сводка теперь требует идемпотентности обработки (повтор `build_summary` не должен слать два сообщения) — ключ `task_id`; для авто-сводки дополнительно `summary_dispatch`.
- (−) Появляется новый тип задачи (`build_summary`) и non-LLM обработчик (ADR-0013).
- Заметка автору: п.3 (убрать прямой publish адаптером) помечен как решение под вето автора.
