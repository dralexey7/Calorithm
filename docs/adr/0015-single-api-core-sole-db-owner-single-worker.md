# ADR-0015 — Единый `api-core` (единственный владелец БД) и один stateless async-воркер

Статус: принято · Дата: 2026-06-03 · Связано: `architecture.md` §3, §4, §5, §9; `contracts.md` §1, §3; ADR-0001, ADR-0003, ADR-0005, ADR-0008
· **Supersedes: ADR-0013** · **Amends: ADR-0012, ADR-0009**

## Context

Прошлый чистовик дробил обработку на `core-worker` (LLM), `diary-worker` (non-LLM сводки) и `scheduler`. Практика показала, что это дробление избыточно для реальной природы работы:

- **Сводки** (US-007 по запросу и US-008 авто) = чтение БД + форматирование. Это **синхронная**, дешёвая, не лимитируемая работа. Гонять её через очередь и отдельный `diary-worker` (ADR-0013) — сложность без выгоды: добавляет задачу `build_summary`, второй топик `tasks.diary`, второй деплой-юнит и второй путь идемпотентности.
- **Работа с пользователями** (резолв, настройки, primary, удаление) — тоже синхронная, над одной-двумя строками.
- **Асинхронность реально платит только на внешних, медленных, лимитируемых вызовах** — LLM и OFF. Только пайплайн обработки сообщения о еде (intent → parsing → nutrition) обязан быть async и под лимитерами.

Параллельно нужно сохранить инвариант ADR-0001 «одна схема — один владелец» и не вернуться к анти-паттерну «два сервиса пишут в одну БД»: если выделять отдельный воркер, нельзя позволить и `api-core`, и воркеру писать в Postgres.

## Decision

**1. Единый `api-core` (FastAPI) делает всю синхронную работу и является единственным владельцем БД (единственный процесс с доступом к Postgres).**
В нём — резолв/регистрация пользователей (US-001), настройки (US-005), смена primary (ADR-0009), **сводка по запросу и авто-сводка — снова синхронно** (чтение БД + форматирование, US-007/US-008), мягкое удаление (US-009), и **persist записей еды**. Внутри сохраняется модульная структура с владением схемами per-module (`users`, `diary`), чтобы будущий вынос модулей в сервисы оставался механическим (ADR-0001).

**2. Один stateless async-воркер `processing-worker` — чистый вычислитель пайплайна обработки сообщения. БЕЗ доступа к БД.**
Он принимает задачу с текстом, выполняет: классификация намерения (intent) → парсинг (parsing) → определение КБЖУ (nutrition: OFF через OFF-лимитер, fallback LLM через LLM-лимитер) и **возвращает структурный результат** (распознанные позиции + КБЖУ + источники per-item + артефакты трассировки). Конкурентность K и централизованные лимитеры — без изменений (ADR-0005, ADR-0007). Воркер **ничего не пишет в БД** — этим он не конкурент `api-core` за владение БД.

**3. Механика возврата результата воркера и доставки в канал (orchestrate-by-api-core).**
`api-core` оркеструет, воркер только считает; доставка идёт тем же брокерным транспортом, что и раньше (консистентно с ADR-0008):

| Хоп | Транспорт | Кто пишет в БД |
|---|---|---|
| адаптер → `api-core` | HTTP `POST /v1/messages` (канонический вход, ADR-0012) | — |
| `api-core` → воркер | publish `ProcessingTask` в `tasks.processing` | — |
| воркер → `api-core` | publish `ProcessingResult` в `results.processing` (воркер не пишет в БД) | — |
| `api-core` ← `results.processing` | consume, **persist записи** (модуль `diary`), сформировать `Result` | **`api-core`** |
| `api-core` → адаптер | publish `Result{kind=...}` в `results.<channel>` (ADR-0008) | — |
| адаптер ← `results.<channel>` | доставка пользователю | — |

Обоснование выбора брокерного обратного хопа (а не HTTP callback воркер→api-core): один транспорт на всю асинхронную границу (Redis Streams через `MessageBus`), at-least-once + идемпотентность по `task_id` уже встроены, воркер остаётся без inbound-HTTP и stateless. `api-core` — **единственный писатель в БД и единственный публикатор в `results.<channel>`**.

**4. Сводка — синхронный эндпоинт.** `GET /v1/summary` снова возвращает сводку прямо в HTTP-ответе (US-007). Авто-сводку (US-008) `scheduler` триггерит дёрганьем внутреннего синхронного механизма `api-core` (см. ADR-0017), который читает БД, форматирует и публикует `Result{kind=daily_summary}` в `results.<channel>`. `tasks.diary`, `build_summary` и `diary-worker` **удаляются**.

**5. `scheduler` остаётся stateless-триггером 09:00** (ADR-0009), но триггерит синхронную генерацию/доставку сводки в `api-core`, сам в БД/LLM не ходит — см. ADR-0017.

Инварианты ADR-0001 сохранены: внутренняя развязка модулей и владение схемами per-module внутри `api-core`; единые точки `llm`/`off_client` с лимитерами; миграции только Alembic; мониторинг с самого начала (ADR-0010).

## Consequences

- (+) Значительно проще: один воркер вместо двух, один топик задач (`tasks.processing`) вместо `tasks.llm`+`tasks.diary`, сводка без очереди и без задачи `build_summary`.
- (+) **Единственный владелец БД** — снят риск «два сервиса на одну БД»; воркер чисто вычислительный, легко тестируется и масштабируется репликами без координации записи.
- (+) Сводка по запросу — мгновенная (синхронный HTTP), без задержки очереди.
- (+) Меньше деплой-юнитов (было 9 → стало 8: удалён `diary-worker`).
- (−) Появляется обратный хоп воркер→`api-core` через брокер (`results.processing`) и потребитель этого топика в `api-core`. Осознанная цена за «один владелец БД» + «воркер без БД». Сложность хопа эквивалентна прежней доставке `core-worker`→`results.<channel>`, просто получатель теперь `api-core`, а не адаптер.
- (−) `api-core` теперь и HTTP-фасад, и потребитель `results.processing`. Это два режима в одном процессе (web + consumer-loop) — приемлемо для одного VPS; при росте `api-core` делится на web и orchestrator без смены контрактов (обратимо).
- Обратимо: воркер по-прежнему выносится в сервис (он уже за сетевой границей брокера); модули внутри `api-core` сохраняют владение схемами для будущего разреза.
