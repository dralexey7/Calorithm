# ADR-0003 — Очередь обработки и отложенный ответ

Статус: принято · Дата: 2026-06-02 · Связано: `architecture.md` §4.2, §5

## Context

Обработка сообщения о еде = несколько LLM-вызовов (классификация US-017 + парсинг US-002 + до N оценок КБЖУ US-004), это секунды. Синхронный путь блокировал бы адаптер и плохо переживал бы всплески и падения. Telegram-путь должен оставаться отзывчивым.

## Decision

**Паттерн очереди обработки**: входящее сообщение → очередь → воркер (LLM-работа). Адаптер сразу освобождается. Результат разбора **доставляется с задержкой** обратно в канал-источник (механизм — ADR-0008). Жёсткого синхронного UX нет.

**Промежуточная индикация «обрабатываю…» — опциональная деталь канала-адаптера, не требование ядра.** Ядро гарантирует только отложенную доставку результата. Адаптер вправе:
- показать нативную индикацию канала (например, Telegram chat action `typing`), либо
- не показывать индикацию вовсе — ради простоты.

Выбор индикации не влияет на контракты ядра и брокера; это решение конкретного адаптера (свобода реализации в рамках ADR-0002).

Минимизация синхронных путей и асинхронная сводка по запросу — см. ADR-0012; в `core-api` синхронным остаётся только то, что обязано (резолв/настройки/primary, enqueue), всё остальное — через очередь.

## Consequences

- (+) Адаптер не блокируется; всплески сглаживаются глубиной очереди; падение воркера переживается (at-least-once, ADR-0004).
- (+) Разделение «приём» и «обработка» позволяет независимо масштабировать воркеры и встроить LLM-лимитер (ADR-0005).
- (+) Индикация необязательна → адаптер можно держать тоньше; отсутствие индикации не ломает UX, т.к. результат всё равно придёт.
- (−) UX асинхронный: между приёмом и ответом есть задержка. Если индикация выключена, пользователь не видит явного «принято» до самого ответа — приемлемо для MVP, обратимо включением chat action.
- (−) Нужна корректная адресация отложенного ответа и идемпотентность обработки (повтор доставки задачи) — ключ `task_id` → `entries.source_task_id`.
