# ADR-0001 — Модульный монолит ядра со строгой развязкой

Статус: принято · Дата: 2026-06-02 · Связано: `architecture.md` §3, §6, §10

## Context

Продуктовый принцип Calorithm — «ядро + подключаемые каналы». Логики много (users, intent, parsing, nutrition, diary, scheduler), нагрузка низкая (1–2 пользователя, один разработчик, один VPS). Полноценные микросервисы сразу — преждевременная сложность (нарушение «start small / boring tech»). Но и монолит с переплетёнными модулями и общими таблицами потом невозможно безболезненно разрезать на сервисы, а расширяемость (новые каналы, будущие модули вроде целей US-011) заявлена как требование.

## Decision

Ядро — **модульный монолит со строгой развязкой**:
- развязка по коду И по схемам БД; **одна схема — один владелец-модуль** (`users`, `diary`; `scheduler` — stateless-триггер без своей схемы, `summary_dispatch` принадлежит `diary` — см. `architecture.md` §6, ADR-0013);
- запрет кросс-схемного доступа (нет чужих repository, нет кросс-схемных FK, нет общих таблиц);
- межмодульное общение — событиями через брокер (`bus`) либо публичным сервисным интерфейсом с типизированными Pydantic DTO;
- цель — **механический вынос** любого модуля в отдельный сервис заменой in-process вызова на HTTP/событие без переписывания логики.

## Consequences

- (+) Простой деплой и разработка сегодня, но архитектурно готово к разрезанию на сервисы без рефакторинга логики.
- (+) Чёткие границы делают ревью объективным и ограничивают «расползание» связей.
- (−) Дисциплина дороже «просто сджойнить таблицы»: данные другого модуля — только через событие/DTO, иногда с дублированием. Это осознанная цена развязки.
- (−) Нет кросс-схемной транзакционной целостности на уровне БД — согласованность обеспечивается событиями и идемпотентностью.
- Нарушение развязки трактуется как дефект и блокирует ревью (`conventions.md` §3).
