# ADR-0017 — Сквозная трассируемость «сообщение → результат по КБЖУ»

Статус: принято · Дата: 2026-06-03 · Связано: `architecture.md` §4.2, §6, §8; `contracts.md` §3.1, §3.2; US-002, US-004, US-017, R4; ADR-0010, ADR-0015, ADR-0016

## Context

Пайплайн обработки сообщения проходит несколько шагов (intent → parsing → nutrition с OFF/LLM-fallback) в `processing-worker`, который **не пишет в БД** (ADR-0015). При неверном результате (плохой парсинг, неожиданный источник КБЖУ, ложная классификация) нужно уметь разобрать, **что именно** дало сбой, не воспроизводя весь путь вручную. Логов без корреляции недостаточно: задачи асинхронны, идут через брокер, проходят несколько процессов.

## Decision

**1. Корреляция по `task_id` сквозь весь путь.** `task_id` генерируется `api-core` при enqueue и протягивается: `ProcessingTask` → логи/метрики воркера на каждом шаге → `ProcessingResult` → persist (`entries.source_task_id`) → `Result` в `results.<channel>`. Все логи и метрики на горячем пути обработки сообщения помечаются `task_id` (и `user_id`). Это позволяет собрать полный путь одного сообщения по одному ключу.

**2. Персист промежуточных артефактов трассировки.** При persist записи (в `api-core`, модуль `diary`) вместе с `entry` сохраняются артефакты обработки для разбора ошибок. Явно персистим:

- `raw_text` — исходный текст пользователя (уже было; уровень `entry`);
- `intent_result` — итог классификации (про еду / не про еду + уверенность/метка, если есть);
- `parse_artifact` — что выдал парсинг (распознанные позиции до нутриции: имена, количества, флаг оценочного веса);
- per-item `source` (`OFF | LLM`) — уже было (`entry_items.source`), фиксируем как часть трассы «откуда КБЖУ»;
- `model_meta` — модель/версия промпта LLM и/или версия логики, использованные при обработке (для воспроизводимости);
- `source_task_id` — ключ корреляции (уже было).

Артефакты хранятся в схеме `diary` (поля `entry` либо отдельная таблица `entry_trace` 1:1 — свобода реализации в рамках владения схемой `diary`). Объём малый, пишется один раз при persist.

**3. Что НЕ персистим в MVP:** полные промпты/сырые ответы LLM и полные HTTP-тела OFF — это объём и потенциально PII/стоимость хранения; при необходимости — отдельным решением. Достаточно структурных артефактов выше + `model_meta` для воспроизведения.

**4. Метрики качества** (ADR-0010) считаются из тех же артефактов: доля КБЖУ из OFF vs LLM-fallback, успешность парсинга/классификации.

## Consequences

- (+) Любой спорный результат разбирается по `task_id`: видно текст, итог intent, что распарсилось, откуда взялось КБЖУ, какой моделью.
- (+) Воркер остаётся без БД (ADR-0015): он лишь возвращает артефакты в `ProcessingResult`, персист — в `api-core`.
- (+) База для метрик качества и для повторного разбора (R4) без повторного прогона LLM.
- (−) Небольшой рост схемы `diary` и payload `ProcessingResult` (несут артефакты). Объём малый; приемлемо.
- (−) `model_meta`/версии промптов нужно дисциплинированно проставлять в модуле `llm` — выносится в единую точку LLM (ADR-0006), проверяется ревью.
- Изменения схемы под артефакты — ревизией Alembic (ADR-0014), только в схеме `diary`.
