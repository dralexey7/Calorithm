# ADR-0009 — Primary-канал для авто-сводки при активной мульти-канальности

Статус: принято · Дата: 2026-06-02 · Связано: `architecture.md` §4.3, §6, US-008, A6

## Context

У пользователя **несколько каналов могут быть активны одновременно** (активная мульти-канальность). Немедленный ответ на сообщение однозначен — идёт в канал-источник (ADR-0008). Но авто-сводка в 9:00 (US-008) не привязана к входящему сообщению → нужно решить, куда её слать. Варианты: во все активные каналы либо в один выделенный.

(В черновике v2 рекомендовалось «во все активные каналы». Автор зафиксировал иное решение — см. ниже.)

## Decision

Авто-сводка в 9:00 доставляется **только в основной (primary) канал** пользователя. Primary хранится флагом `is_primary` в `channel_identities`; инвариант — ровно один primary среди активных каналов. Пользователь может **сменить primary** (эндпоинт `POST /v1/users/primary-channel`). Немедленные ответы по-прежнему идут в канал-источник (ADR-0008). Если за прошедший день записей не было — сводка не отправляется (A6).

## Consequences

- (+) Нет дублирования сводки по нескольким каналам; предсказуемое место получения утреннего отчёта.
- (+) Пользователь управляет, куда приходит авто-сводка, не влияя на немедленные ответы.
- (−) Нужно поддерживать инвариант «ровно один primary» и эндпоинт смены; `scheduler` резолвит primary через `users`.
- (−) Если primary-канал стал неактивен, сводка может не дойти — обрабатывается как ошибка доставки (метрика) и кандидат на будущую логику фолбэка (вне MVP).

> Уточнение топологии (ADR-0012, ADR-0013): авто-сводку **запускает** отдельный компонент `scheduler` (он только триггерит — ставит задачу `build_summary` в очередь по расписанию), а **строит и доставляет** её non-LLM обработчик `diary-worker` (тот же код генерации сводки, что и для сводки по запросу US-007). `scheduler` не строит сводку сам и не делает LLM-вызовов. Идемпотентность дубля по-прежнему держит `summary_dispatch (UNIQUE user_id, local_date)` — таблица во владении модуля `diary` (пишет `diary-worker`); `scheduler` к ней не обращается и в БД не пишет (stateless-триггер, ADR-0013).
