# ADR-0014 — Изменения схемы БД только через миграции (Alembic)

Статус: принято · Дата: 2026-06-02 · Связано: `architecture.md` §9, §10; `conventions.md` §1, §3a, §9 (DoD)

## Context

Модель данных разделена на схемы-владельцы (`users`, `diary` — ADR-0001) и будет эволюционировать (например, добавление хранения исходного текста сообщения — `entries.raw_text`). Без дисциплины изменений схемы появляются ручные `ALTER` в проде, дрейф схемы между средами и невоспроизводимое состояние БД. Стек уже фиксирован (Python · PostgreSQL · SQLAlchemy-совместимый async-драйвер), нужен стандартный инструмент миграций.

## Decision

**Любые изменения схемы БД оформляются только через миграции. Ручные `ALTER`/`CREATE`/`DROP` в проде запрещены.**

- Инструмент миграций — **Alembic** (добавлен в стек, `architecture.md` §10, `conventions.md` §1; правила — `conventions.md` §3a).
- Каждое изменение схемы = ревизия Alembic в репозитории; применение — только прогоном миграций (в т.ч. при деплое compose).
- Миграции **обратимы**: каждая ревизия имеет рабочий `downgrade` (где это технически возможно; необратимые шаги — явно отмечены и обоснованы в ревью).
- Развязка схем сохраняется: ревизии не вводят кросс-схемных FK (ADR-0001).
- Включено в Definition of Done (`conventions.md` §9, п.9): при изменении схемы — приложена миграция, она обратима и применяется на чистой БД.

## Consequences

- (+) Воспроизводимое состояние БД во всех средах; нет дрейфа схемы.
- (+) История изменений схемы под ревью и версионированием рядом с кодом.
- (+) Деплой остаётся «one-shot» (миграции — часть запуска), проект деплоибелен (workflow п.3).
- (−) Дополнительный шаг при изменении модели данных (написать ревизию) — приемлемая дисциплинарная цена.
- (−) Требуется аккуратность с `downgrade` для необратимых операций (drop column с данными) — отмечается в ревью.
