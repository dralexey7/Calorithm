# ADR-0008 — Доставка отложенного результата через топик в брокере

Статус: принято, **дополнен ADR-0015** · Дата: 2026-06-02 · Связано: `architecture.md` §4.2, `contracts.md` §3.2; ADR-0015

> **Дополнен ADR-0015 (2026-06-03):** механизм доставки в адаптер (`results.<channel>`) и асимметрия границы адаптера — без изменений. Но теперь воркер (`processing-worker`) **не публикует напрямую в `results.<channel>`** и не пишет в БД: он возвращает результат в `api-core` через топик `results.processing`; `api-core` персистит запись и сам публикует `Result` в `results.<channel>`. То есть единственный публикатор `results.<channel>` — `api-core` (тем же транспортом, что описан ниже).


## Context

Адаптеры — отдельные процессы (ADR-0002), поэтому воркер не может вернуть результат обработки (ADR-0003) прямым вызовом. Нужен механизм доставки отложенного ответа обратно в канал-источник. Варианты: callback-HTTP в адаптер либо топик/очередь результатов в брокере.

## Decision

**Топик результатов в брокере, на который подписан адаптер**, партиционированный по каналу: `results.telegram` (на будущее `results.<channel>`).
1. Адаптер передаёт `channel`, `channel_user_id`, `reply_to` (chat_id/message_id), `text` в `core-api` по HTTP (`POST /v1/messages`), который резолвит пользователя, формирует `Task{task_id, ...}` и публикует его в очередь задач (`tasks.llm`/`tasks.diary` по типу — ADR-0013; канонический входящий путь — ADR-0012).
2. Воркер-потребитель (`core-worker` для LLM-задач, `diary-worker` для сводок) по завершении публикует `Result{task_id, channel, channel_user_id, reply_to, payload}` в топик результатов своего канала.
3. Адаптер подписан на топик своего канала (consumer group на адаптер-инстанс), форматирует и отправляет в транспорт по `reply_to`.

Ответ на конкретное сообщение всегда идёт **в канал-источник** (`channel`/`reply_to` из исходной задачи) — без неоднозначности.

**Граница для адаптера асимметрична (снятие неоднозначности прошлого чистовика):** адаптер общается с брокером **только на чтение** результатов (`results.*`). Публикацию `Task` в очередь задач адаптер **не делает** — он не знает внутренних топиков задач; постановку в очередь выполняет `core-api` за версионируемой HTTP-границей. Это чистая граница и не противоречит «минимуму синхронного» (синхронен лишь быстрый non-blocking enqueue, не обработка — ADR-0012).

## Consequences

- (+) Воркеру не нужен сетевой адрес/доступность адаптера — только имя топика по `channel`. Сохраняет тонкость адаптера и развязку (ADR-0001/0002).
- (+) Consumer group маршрутизирует и переживает рестарт адаптера (at-least-once, PEL); симметрично входящей очереди — один транспорт.
- (+) Несколько инстансов/каналов масштабируются добавлением подписчиков.
- (−) Доставка ответа — at-least-once → адаптер должен корректно обрабатывать возможный повтор отправки (идемпотентность на стороне отправки в канал).
- (−) Лишний хоп через брокер вместо прямого ответа — осознанная цена развязки процессов.
- (+) Адаптер не зависит от имён внутренних топиков задач — только от HTTP-контракта `core-api` и имени `results.<channel>`. Граница задач версионируема независимо от адаптера.
