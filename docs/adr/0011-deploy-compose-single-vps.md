# ADR-0011 — Деплой: docker-compose на одном VPS, Telegram long polling

Статус: принято, **обновлён ADR-0015** · Дата: 2026-06-02 · Связано: `architecture.md` §9, workflow п.3; ADR-0015

> **Обновлён ADR-0015 (2026-06-03):** деплой-юнитов стало **8** (удалён `diary-worker`); `core-worker` переименован в `processing-worker` (один stateless async-воркер LLM/OFF-пайплайна, без БД); `tasks.diary` удалён, задачи идут в один топик `tasks.processing`; добавлен обратный топик `results.processing` (воркер → `api-core`). Перечень ниже отражает прежнее состояние; актуальный перечень — `architecture.md` §9.


## Context

Архитектура распределённая по процессам (отдельные адаптеры, воркер, брокер — ADR-0002/0003/0004), но нагрузка низкая (1–2 пользователя), разработчик один, и деплой должен «стоять с самого начала» (workflow п.3). Нужен один деплой-таргет, простой и держащий проект деплоибельным постоянно. Полноценный k8s/мульти-хост — преждевременная сложность.

## Decision

**Оркестрация — docker-compose на одном VPS.** Деплой-юниты (9 — обновлено в ADR-0013, ранее было 7):
1. `channel-telegram` · 2. `core-api` (FastAPI) · 3. `core-worker` (LLM-only, K=2–4) · 4. `diary-worker` (non-LLM, сводки US-007/US-008) · 5. `scheduler` (триггер 9:00) · 6. `broker` (Redis: `tasks.llm`+`tasks.diary`+события+результаты+лимитеры) · 7. `postgres` (схемы users/diary) · 8. `prometheus` · 9. `grafana`.

Миграции схемы применяются через Alembic как one-shot шаг до старта сервисов (ADR-0014).

Telegram — **long polling** в MVP (без публичного HTTPS/вебхука). `core-api` слушает HTTP только внутри compose-сети (плюс `/metrics`). Граница ядро/адаптер реальная (сеть), но всё на одном хосте.

## Consequences

- (+) Один деплой-таргет, простой запуск/рестарт; распределённость реальная, но управляемая.
- (+) Long polling снимает необходимость публичного HTTPS/вебхука и TLS-обвязки в MVP.
- (+) Финальный деплой — формальность, т.к. проект деплоибелен с Фазы 1.
- (−) Один VPS = единая точка отказа; горизонтального масштабирования между хостами нет (вне scope MVP).
- (−) Long polling менее эффективен, чем вебхук, при росте нагрузки — обратимо (переход на вебхук) без изменения ядра.
- Обратимо: при росте — реплики воркера (ADR-0005), затем мульти-хост/оркестратор.
